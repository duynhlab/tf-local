# Terragrunt — research & adoption plan (NOT implemented yet)

> Status: **planning only**. Current repo uses **plain Terraform roots** + partial
> backend config (`-backend-config=backend.hcl`). This doc captures how Terragrunt
> would DRY provider/backend/state across many accounts when the repo grows.
> Source: context7 `/gruntwork-io/terragrunt` docs.

## 1. Why consider it

Plain Terraform can't share `provider`/`backend` config across separate root
modules (provider config is root-only, not inherited; backend blocks can't use
variables). Today we handle this with per-root `providers.tf` + `backend.hcl`.
That's fine for a handful of roots, but with **N accounts × M regions × K
components** the boilerplate (provider + backend + assume_role + state key) repeats
everywhere. Terragrunt removes that repetition by **generating** those files from
one place.

## 2. Core mechanisms

### `generate` blocks (the replacement for our symlink/copy-paste)
A single `root.hcl` generates `backend.tf` and `provider.tf` into every unit at
runtime — no symlinks, no copy-paste:

```hcl
# root.hcl
remote_state {
  backend = "s3"
  generate = { path = "backend.tf", if_exists = "overwrite_terragrunt" }
  config = {
    bucket       = "dnl-tfstate-${local.account_id}"
    key          = "${path_relative_to_include()}/terraform.tfstate"  # key follows folder path
    region       = local.region
    encrypt      = true
    use_lockfile = true   # S3-native locking, no DynamoDB
  }
}

generate "provider" {
  path      = "provider.tf"
  if_exists = "overwrite_terragrunt"
  contents  = <<EOF
provider "aws" {
  region = "${local.region}"
  assume_role { role_arn = "arn:aws:iam::${local.account_id}:role/terraform" }
  default_tags { tags = ${jsonencode(local.tags)} }
}
EOF
}
```

### `include` — units pull the root config
```hcl
# envs/dev/ap-southeast-1/networking/terragrunt.hcl
include "root" { path = find_in_parent_folders("root.hcl") }
terraform { source = "../../../../..//modules/networking/vpc" }  # or a thin wrapper
inputs = { vpc_cidr = "10.100.0.0/16", ... }
```

### Account/region/env config files (DRY inputs)
Standard Gruntwork layout — config bubbles up via `read_terragrunt_config` +
`find_in_parent_folders`:
```
envs/
  account.hcl      # account_id, account_name (per account dir)
  region.hcl       # region (per region dir)
  env.hcl          # environment name (per env dir)
  <component>/terragrunt.hcl   # include root + source + inputs
```

### `dependency` — pass outputs between units (replaces terraform_remote_state)
```hcl
dependency "networking" {
  config_path = "../networking"
  mock_outputs = { vpc_id = "vpc-mock", app_subnet_ids = ["subnet-mock"] }  # for plan before apply
}
inputs = { subnet_ids = dependency.networking.outputs.app_subnet_ids }
```

### `run --all` (formerly `run-all`)
`terragrunt run --all apply` walks the dependency graph and applies units in order
across all envs/components.

### Terragrunt Stacks (newer)
`terragrunt.stack.hcl` declares reusable groups of units — good for "spin up a full
env" as one unit-of-deployment. Evaluate once stable.

## 3. How it maps onto THIS repo

| Today (plain TF) | With Terragrunt |
|---|---|
| per-root `providers.tf` (real AWS) | generated by `root.hcl` `generate "provider"` |
| per-root `backend.tf` + `backend.hcl` | generated by `remote_state` block (key via `path_relative_to_include()`) |
| `terraform_remote_state` data source | `dependency` block + `mock_outputs` |
| `modules/*` (unchanged) | unchanged — Terragrunt wraps roots, not modules |
| account ids as variables | `account.hcl` per account dir |

Modules in `modules/` stay exactly the same. Only the **root layer** (`envs/*`)
changes from `.tf` roots to thin `terragrunt.hcl` units.

## 4. Pros / cons

**Pros:** zero provider/backend boilerplate; per-account `assume_role` generated;
state keys auto-derived from path; cross-unit `dependency` graph + `run --all`;
mature (Gruntwork), huge adoption.

**Cons:** extra binary + version pin (`tenv`/`mise`); generated `*.tf` are not
in VCS (some teams dislike); learning curve; `mock_outputs` foot-guns; plain
`terraform` commands no longer the entrypoint.

## 5. Decision / when to adopt

- **Now:** stay on plain Terraform roots (real providers + `-backend-config`).
  Few roots; boilerplate is small and explicit.
- **Adopt Terragrunt when** any of: >10 live roots, ≥3 accounts actively managed,
  repeated `assume_role`/backend boilerplate becomes error-prone, or we want
  `run --all` orchestration + a dependency graph across components.
- **Migration is incremental:** add `root.hcl` + per-unit `terragrunt.hcl`
  alongside existing `.tf` (delete `providers.tf`/`backend.tf` once generated),
  one env at a time. State keys must match existing keys to avoid re-create.

## 6. Pin & tooling (when adopted)
- Pin Terragrunt + Terraform via `tenv`/`mise` (`.terraform-version`,
  `.terragrunt-version`).
- CI: `terragrunt hcl fmt`, `terragrunt run --all plan` per account.
- Keep `modules/` provider-agnostic (no provider blocks) — already the case.
